# Work one lane of a chappe plan

A lane is one agent working on one set of files, in its own worktree, next to other lanes running at the same time. Use this skill to write a lane brief, or to follow one.

## Before you start

1. Read the approved plan file the brief names, and `AGENTS.md`.
2. Branch from the current `main`, not from the worktree's base commit:

   ```sh
   git fetch origin && git checkout -B <lane-branch> origin/main
   ```

3. Read the brief's file list: the files your lane owns, and the files other lanes own. Never edit another lane's files. If you need a change there, keep it minimal and say so in your report.

## Isolation

Each lane gets its own:

| Resource | Rule |
|---|---|
| Scratch files | the session scratchpad, under a `<lane>_` prefix |
| Docker compose project | `-p <lane>...` |
| Host ports | the range the brief gives (for example 16000-16999) |
| Waiting on a process | wait on its PID; never loop on `pgrep -f`, which matches itself |

Other lanes run on the same machine: check the load average before timing anything, and rerun a failure on its own before calling it a regression.

## While you work

- Write each new test first and run it against the old code to see it fail.
- Share code, do not copy it (`AGENTS.md`). Export a helper from the module that owns the concept.
- Do not edit `CHANGELOG.md`, `apps/chappe_sip/docs/features.md` or the compliance files unless the brief says so: the integrator writes user docs once lanes merge.
- Leaf apps (`chappe_rtpengine`, `chappe_mix`, `chappe_esl`) stay SIP-free.

## Before you report

```sh
make check
```

It must pass: fmt, compile, lint, xref, dialyzer, eunit, ct, and the coverage floor. Run the interop targets your change touches (`make interop-sbc`, `make interop-esl`, `make interop-conformance`, ...).

## Commits

- About two commits per lane.
- One imperative, lowercase subject. A body only for a non-obvious why.
- No `Co-Authored-By`, no "generated by" trailer.
- Never the em-dash character, never the word "comprehensive".
- Do not push and do not open a PR: the integrator does.

## Report

Under 450 words:

- branch and commit SHAs;
- the API added (signatures, message shapes);
- test results with counts, including interop;
- where you departed from the plan, and why;
- what is left undone, with the reason.

## Notes

- A plan detail that turns out wrong once you read the code: take the simplest correct alternative and say so in the report.
- Stuck on the same failure after two or three attempts: stop and report what you tried.
